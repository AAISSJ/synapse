# 객체 · 블록 · 파일 스토리지 비교

접근 방식과 앱에서 맡는 역할로 비교한다. 실제 기능·성능·비용은 제품과 구성에 따라 확인한다.

| 항목 | 객체 스토리지 | 블록 스토리지 | 파일 스토리지 |
| --- | --- | --- | --- |
| 접근 방식 | 버킷 안의 객체를 키와 API로 조회 / key에 객체를 통째로 매핑하고 HTTP API로 접근함 | 서버에 디스크처럼 연결 /  디스크를 고정 크기 블록 단위로 다룸. OS가 그 위에 파일시스템을 올려서 씀 | 폴더/파일 계층 구조로 다루고 여러 서버가 공유할 수 있음 / 파일·디렉터리 경로로 접근. 공유 서비스는 NFS·SMB 등 사용 |
| 앱이 보는 단위 | 데이터 바이트와 메타데이터를 가진 객체 | 주소를 지정해 읽고 쓰는 블록 장치 | 파일·디렉터리·권한 등 파일 시스템 인터페이스 |
| 변경 방식 | 일반적으로 객체 교체·새 버전 저장. 부분 읽기·업로드 기능은 서비스별 확인 | 블록 단위 읽기·쓰기. 위에 파일 시스템·DB 저장 구조 구성 | 파일 열기·부분 수정 등. 프로토콜의 잠금·캐시 의미를 확인 |
| 주 활용처 | 이미지·PDF·동영상·백업·분석 데이터 원본 | VM OS·데이터 디스크, DB 파일·로그 | 여러 서버의 공유 파일과 파일 시스템 기반 기존 앱 |
| 대표 제품 | Amazon S3 · Cloudflare R2 · GCS · Azure Blob Storage | Amazon EBS · Azure Managed Disks · Google Cloud Hyperdisk | Amazon EFS · Azure Files · Google Cloud Filestore |
| 공유·동시 접근 | 여러 클라이언트가 API로 접근. 동시 변경·버전·조건부 쓰기를 설계 | 다중 연결 지원과 앱·파일 시스템의 공유 안전성은 별개 | 여러 클라이언트가 공유 가능. 파일 잠금·캐시·앱의 쓰기 충돌 관리 필요 |
| DB와의 관계 | 파일 원본을 두고 DB에 메타데이터 저장. 객체 기반 DB·분석 엔진은 별도 설계 | 일반적인 자체 운영 DB 데이터 파일의 저장 기반 | DB가 해당 파일 시스템·프로토콜을 지원하는지 검증. 모든 DB에 적합한 것은 아님 |
| 비용·성능 판단 | 저장량·요청 수·전송·조회·클래스·보존 조건 | 용량·IOPS·처리량·지연·VM I/O 한도 | 용량·처리량·파일·메타데이터 작업·네트워크·등급 |
| 복구·보안 | 버전·수명 주기·백업·객체 권한·서명 URL 범위 | 스냅샷·백업·장애 영역·DB 일관성·디스크 권한 | 백업·스냅샷·공유 권한·네트워크·잠금과 복구 절차 |
