# Redis · PostgreSQL · MongoDB 비교

저장소는 데이터 모델·정합성·접근 패턴·운영 요구에 따라 선택한다. 실제 성능과 처리 가능한 규모는 워크로드와 설정에 따라 달라진다.

| 항목 | Redis | PostgreSQL | MongoDB |
| --- | --- | --- | --- |
| 저장 방식 | 메모리 중심. RDB 스냅샷·AOF로 영속화 가능. | 디스크 영속 저장과 메모리 캐시를 함께 사용. | 디스크 영속 저장과 메모리 캐시를 함께 사용. |
| 성능 특성 | 키 기반의 단순 조회·갱신에서 낮은 지연 시간에 유리. | 쿼리·인덱스·데이터 규모·동시성에 따라 달라짐. | 쿼리·인덱스·데이터 규모·동시성에 따라 달라짐. |
| 데이터 모델 | 키-값과 String·Hash·List·Set·Sorted Set 등 자료구조. | 관계형 테이블·스키마·제약 조건. JSONB도 지원. | BSON 문서 모델. 필드 구성이 다른 반정형 데이터에 유연함. |
| 쿼리 기능 | 키 기반 명령과 자료구조 연산 중심. 관계형 JOIN과는 접근 방식이 다름. | SQL·JOIN·집계와 다양한 인덱스를 활용한 복합 조회. | 필드 쿼리·인덱스·집계 파이프라인과 $lookup 등 지원. |
| 트랜잭션·원자성 | 원자적 명령·MULTI/EXEC·Lua 지원. 실행 오류가 이전 변경을 자동 롤백하지 않음. | ACID 트랜잭션과 격리 수준 제공. 설정에 따른 보장 범위 확인 필요. | 문서 단위 원자성 및 지원 배포 구성에서 다중 문서 트랜잭션 제공. |
| 용량·확장 | 메모리 용량·비용이 주요 제약. 데이터 분할과 영속화·복구 전략 고려. | 디스크 확장, 읽기 복제·파티셔닝·데이터 분할 등을 검토. | 디스크 확장, 복제·샤딩으로 확장 가능. |
| 시스템 내 역할 | 캐시·세션·실행 상태·큐 등 저지연 보조 계층에 주로 활용. | 정합성이 중요한 업무 데이터의 원본 저장소. | 문서·콘텐츠의 원본 또는 대화·실행 기록 저장소. |
| 주요 활용처 | 캐시, 세션, rate limit, 랭킹, 작업 큐, Pub/Sub 알림. | 사용자, 주문, 결제, 권한, 재고 등 핵심 업무 데이터. | 콘텐츠, 상품 카탈로그, 대화, 이벤트·실행 로그. |
| 적합한 데이터 | 접근 빈도가 높고 빠른 갱신이 필요한 값. 재생성 가능한 캐시·만료가 있는 임시 상태. | 관계가 명확하고 여러 변경의 정합성을 함께 보장해야 하는 데이터. | 구조가 유동적이거나 항목별 필드가 다른 반정형 문서. |
| 설계 시 고려사항 | 캐시와 유실되면 안 되는 작업을 구분. 메모리 비용·내구성·복구·소비자 멱등성 설계. | 쿼리 패턴에 맞는 스키마·인덱스·트랜잭션 경계 설계. 유동적 데이터는 JSONB도 검토. | 문서 분할·크기 제한·인덱스 설계. 여러 문서에 걸친 조회와 트랜잭션 비용 고려. |
| 에이전트 활용 예시 | 단기 컨텍스트·응답 캐시, 호출·예산 카운터, 도구 작업 큐. | 사용자·ACL·에이전트 설정·최종 사용량·과금. pgvector 기반 문서 검색. | 대화 메시지, tool_call·tool_result, 실행 이벤트·오류·지연 시간. |
