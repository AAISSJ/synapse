# 블록 스토리지

다른 이름: Block Storage

주제: 데이터 저장

서버에 블록 장치로 제공되는 저장 공간이다. 그 위에 파일 시스템이나 DB 저장 구조를 구성해 사용한다.

## 내 정리

-   저장 단위: ==데이터를 고정 크기 블록으로 쪼개서 저장하고, 각 블록은 주소(번호)로만 구분됨. == 오브젝트 스토리지는 객체 통째로, 파일 스토리지는 파일과 폴더, DB는 행이나 문서 단위로 저장한다는 점에서 가장 저수준임.
-   주요 용도: ==OS 부팅 디스크, DB 데이터 디스크, 낮은 지연시간과 잦은 랜덤 I/O가 필요한 애플리케이션 저장소==에 주로 씀.
-   구조: ==블록 자체에는 파일이나 폴더 개념이 없어서 OS가 그 위에 파일시스템(ext4, XFS 등)을 올려야 파일로 쓸 수 있음==. 오브젝트 스토리지는 key와 객체의 평평한 매핑, 파일 스토리지는 폴더 트리, DB는 스키마라는 구조를 이미 갖고 있음.
-   접근 방식: ==서버에 디스크처럼 붙여서 OS가 장치(/dev/sdb 등)로 인식하고, 보통 서버 한 대에만 연결됨. == 오브젝트 스토리지는 HTTP API, 파일 스토리지는 NFS 같은 프로토콜로 여러 서버가 마운트하며, DB는 SQL이나 전용 쿼리 언어로 접근함.
-   데이터 찾기: 블록 주소로만 접근할 수 있고 검색 기능은 전혀 없음. 파일 찾기는 위에 올린 파일시스템이, 조건 검색은 DB가 담당하므로 블록 스토리지는 그 아래 계층만 맡음.
-   메타데이터: 블록 단위로는 메타데이터 개념이 거의 없고, 파일 이름이나 권한 같은 정보도 파일시스템이 관리함. 오브젝트 스토리지는 객체마다 사용자 정의 메타데이터를 붙일 수 있고, 파일 스토리지는 이름, 크기, 권한 같은 고정 속성을 가짐.
-   대표 서비스: ==로컬 SSD/HDD, AWS EBS, GCP Persistent Disk, Azure Managed Disk==가 있고, 온프레미스에서는 SAN(iSCSI, Fibre Channel)이나 Ceph RBD를 많이 씀.

---

-   넓은 의미: 블록 단위로 접근하는 저장 장치 전부. 노트북 SSD, 서버의 로컬 NVMe, HDD 모두 포함되고, 파일 스토리지나 오브젝트 스토리지와 대비할 때는 이 의미로 씀.
-   좁은 의미: 클라우드나 데이터센터에서 "블록 스토리지 서비스"라고 하면 보통 AWS EBS, SAN처럼 네트워크로 붙이는 볼륨을 가리킴. 이 맥락에서는 서버에 내장된 SSD를 따로 "로컬 디스크"나 "인스턴스 스토어"라고 불러서 구분하는 경우가 많음.

## 용어

### Amazon EBS

다른 이름: EBS

AWS EC2에 연결해 사용하는 블록 스토리지다. 볼륨 유형에 따라 용량·IOPS·처리량 특성이 다르다. 일반적인 볼륨은 가용 영역 범위에 연결되므로 장애·스냅샷·복구를 설계한다.

### Azure Managed Disks

Azure VM용 관리형 블록 스토리지다. 디스크 등급·성능·중복성·가용성 조건을 선택한다.

### Google Cloud Hyperdisk

다른 이름: Hyperdisk

Google Cloud의 VM용 블록 스토리지 제품군이다. 유형에 따라 용량·성능·연결과 공유 지원 조건이 다르다.

### 볼륨 · 파일 시스템

볼륨은 제공받는 블록 장치이고, 파일 시스템은 그 장치의 공간을 파일·디렉터리로 관리하는 구조다. 블록 저장소 자체가 곧 공유 폴더는 아니다.

### 스냅샷

특정 시점의 저장 상태를 보존하는 기능이다. 실행 중인 DB의 일관성을 보장하려면 쓰기 조율·DB 백업 기능과 복구 절차를 함께 확인해야 한다.

## 디스크처럼 사용하는 저장소
블록 스토리지는 일정 크기의 블록에 읽기·쓰기를 수행할 수 있는 장치 인터페이스를 서버에 제공한다. 운영체제가 파일 시스템을 만들거나 DB가 그 위의 파일·저장 구조를 사용할 수 있다.

VM의 부팅·데이터 디스크, PostgreSQL·MySQL 같은 DB의 데이터 파일과 로그가 대표적인 활용처다. 클라우드의 네트워크 연결 블록 저장소와 호스트에 직접 붙은 로컬 디스크는 수명·연결·장애 특성이 다르다.

## 성능과 공유
작은 랜덤 I/O와 지연, IOPS·처리량·큐 깊이·fsync 동작 등을 워크로드에 맞춰 본다. 제품별 볼륨 성능뿐 아니라 VM의 네트워크·I/O 한도도 영향을 준다.

일부 제품은 여러 서버에 동시 연결하는 기능을 제공하지만, 일반 파일 시스템을 여러 호스트가 동시에 마운트하면 데이터가 손상될 수 있다. 다중 연결 지원과 클러스터 파일 시스템·애플리케이션의 동시성 지원을 별도로 확인한다.

## 가용성과 복구
VM과 볼륨의 수명·삭제 정책을 구분한다. 볼륨의 장애 영역, 스냅샷·복제·백업·복구 시간을 검토한다. 스냅샷이 있다고 해서 DB의 트랜잭션 일관성과 시점 복구가 자동으로 완성되는 것은 아니다.

## Kubernetes와의 관계
CSI 드라이버와 PV·PVC 등을 통해 Pod에 블록 기반 볼륨을 제공할 수 있다. 노드·가용 영역 이동, 연결·해제 시간과 접근 모드를 고려한다. Pod 재생성과 데이터 복구는 같은 작업이 아니다.
