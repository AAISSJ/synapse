# MongoDB

다른 이름: 몽고DB · 몽고디비

주제: DB

BSON 문서 중심 저장소. 유동적인 대화·툴 결과·실행 이벤트 저장 등에 활용할 수 있다.

## 용어

### BSON

MongoDB가 사용하는 문서 표현 형식. JSON과 유사한 구조에 추가 데이터 타입을 지원한다.

### 문서 모델링

접근 패턴에 맞춰 embedding과 reference를 선택한다. 유연한 구조도 검증·인덱스·용량 관리가 필요하다.

### 다중 문서 트랜잭션

지원되는 배포 구성에서 여러 문서의 변경을 트랜잭션으로 처리할 수 있다. 문서 단위 원자성만 있는 DB는 아니다.

## 문서형 데이터 저장
MongoDB는 BSON 문서 기반으로 데이터를 저장한다. 필드 구성이 달라지는 대화 메시지, tool_call·tool_result, 실행 이벤트 등을 모델링하기 편하다. 필드 쿼리·인덱스·집계와 스키마 검증도 지원한다.

## 대화·트레이스 모델링
대화나 실행 전체를 단일 문서에 무한히 추가하지 않는다. 문서 크기 제한(16 MiB)과 갱신 경합을 고려해 메시지·이벤트별 문서 또는 크기가 제한된 묶음을 사용한다.

조회 패턴을 기준으로 embedding과 reference를 선택하고, 자주 조회하는 필드에 인덱스를 설계한다. 한 문서의 변경은 원자적으로 처리되며, 지원되는 배포 구성에서는 다중 문서 트랜잭션도 사용할 수 있다.

실행 트레이스에는 도구 입출력, 오류, 지연 시간과 사용량 등 관찰 가능한 이벤트를 기록한다. 민감정보 보관 범위와 접근 권한을 함께 설계한다.

## 문서형 데이터 저장에 유용한 이유
MongoDB는 데이터를 행·열 중심의 테이블 대신 **BSON 문서**로 저장한다. BSON은 JSON과 비슷한 객체 구조를 표현하면서 날짜·바이너리 등 추가 타입을 지원하는 이진 표현이다. 문서는 컬렉션에 모이며 필드별로 검색·인덱싱할 수 있다. 단순히 JSON 문자열을 저장하는 방식과 다르다.

### 1. 중첩 객체와 배열로 관련 데이터를 함께 표현한다
대화 메시지의 본문·첨부 파일·도구 호출처럼 하나의 데이터에 속한 구조를 문서 안에 담을 수 있다.

```json
{
  "conversationId": "c1",
  "role": "assistant",
  "content": "문서를 검색했습니다.",
  "toolCalls": [
    {"name": "search", "arguments": {"query": "Redis"}, "latencyMs": 120}
  ],
  "metadata": {"model": "example", "schemaVersion": 1}
}
```

항상 함께 읽고 변경하는 작은 데이터는 임베딩하면 JOIN이나 여러 번의 조회를 줄일 수 있다. 다만 참조 관계가 많은 데이터를 무조건 한 문서에 넣는 것은 적절하지 않다.

### 2. 문서마다 필드가 달라도 저장할 수 있다
같은 컬렉션 안에서도 텍스트 메시지·이미지 메시지·도구 실행 결과가 서로 다른 필드를 가질 수 있다. 모든 항목에 동일한 열을 추가할 필요가 없어 구조가 발전하는 콘텐츠에 편리하다.

유연한 스키마는 스키마가 없다는 뜻이 아니다. 필수 필드와 타입은 schema validation으로 제한하고, 애플리케이션에서도 검증한다. 형식 변경 시 schemaVersion, 구버전 읽기 호환성, 기존 문서 변환 전략이 필요하다.

### 3. 문서 내부 필드를 검색·집계한다
중첩 필드와 배열 요소를 조건으로 검색할 수 있고, 복합 인덱스·배열용 multikey 인덱스 등을 활용한다. aggregation pipeline은 필터·변환·그룹 집계 등을 단계적으로 수행한다.

검색 패턴에 맞는 인덱스가 없으면 문서형 저장만으로 빨라지지는 않는다. 인덱스가 늘면 쓰기 비용과 메모리·디스크 사용량도 증가한다.

### 4. 한 문서의 변경을 원자적으로 처리한다
하나의 문서에 대한 쓰기는 원자적이다. 함께 바뀌어야 하는 작은 상태를 같은 문서에 모으면 정합성을 다루기 쉽다. 여러 문서에 걸친 트랜잭션도 지원되는 배포 구성에서 사용할 수 있지만, 비용과 충돌을 고려해 모델링해야 한다.

### 5. 복제와 샤딩을 지원한다
Replica set으로 복제·장애 전환을 구성하고, 샤딩으로 데이터를 여러 샤드에 분산할 수 있다. 내구성·최신성은 write concern과 read concern, 읽기 대상 설정에 영향을 받는다. 샤드 키가 부적절하면 핫스팟이나 여러 샤드를 조회하는 비용이 커진다.

## 임베딩과 참조를 나누는 기준
| 상황 | 설계 방향 |
| --- | --- |
| 작고 크기가 제한되며 함께 읽고 변경하는 데이터 | 한 문서에 임베딩을 검토한다. |
| 독립적으로 갱신·조회하거나 여러 곳에서 공유하는 데이터 | 별도 문서로 저장하고 ID로 참조한다. |
| 끝없이 늘어나는 대화·로그·이벤트 | 메시지·이벤트별 문서 또는 크기가 제한된 버킷으로 분리한다. |
| 복잡한 관계와 여러 엔티티의 동시 변경이 핵심 | RDB와 비교해 트랜잭션·조인·운영 비용을 판단한다. |

BSON 문서는 최대 **16 MiB**이므로 대화 전체나 실행 로그를 하나의 배열에 계속 추가하지 않는다. 큰 파일은 별도 객체 저장소나 GridFS 등을 검토한다. MongoDB도 $lookup으로 조인할 수 있지만, 조인이 많고 관계 제약이 핵심인 모델은 RDB가 더 자연스러울 수 있다.

## 에이전트 시스템에 적용하면
- **대화 메시지**: 메시지별 문서로 저장하고 conversationId와 시각·순번에 맞춰 인덱스를 둔다. 텍스트·이미지·tool_call 등 메시지 유형별 필드를 유연하게 표현한다.
- **실행 트레이스**: runId·stepId를 기준으로 단계·도구 입출력·오류·처리 시간을 저장한다. 커지는 실행은 단계별 문서로 나눈다. 내부 비공개 추론 대신 관측 가능한 실행 이벤트와 결과를 기록한다.
- **보관 기한**: TTL 인덱스로 기간이 지난 기록을 자동 삭제할 수 있다. 삭제는 비동기적으로 진행되므로 정확한 시각의 삭제 보장은 아니다. 민감 정보·감사 기록 정책은 별도로 적용한다.

## PostgreSQL JSONB와의 선택
PostgreSQL도 JSONB의 중첩 데이터·인덱스·검색을 지원하므로 유연한 구조라는 이유만으로 MongoDB를 추가할 필요는 없다. 관계형 데이터와 함께 트랜잭션으로 다뤄야 한다면 JSONB가 단순한 출발점이다. 문서 중심의 접근 패턴과 독립적인 확장·운영 필요가 명확할 때 MongoDB를 비교한다. 쓰기가 많다는 사실만으로 성능 우위를 단정하지 않고 실제 쿼리와 데이터 크기로 측정한다.
