# 객체 스토리지

다른 이름: Object Storage

주제: 데이터 저장

버킷 안의 객체를 키와 API로 식별해 저장·조회한다. 큰 파일 원본과 비정형 데이터를 보관하는 데 널리 사용한다.

## 내 정리

-   **저장 단위**: ==오브젝트 스토리지는 파일 하나를 객체로 통째로 저장함.== 블록 스토리지는 고정 크기 블록, 파일 스토리지는 파일과 폴더, DB는 행이나 문서 단위로 저장한다는 점에서 다름.
-   **주요 용도**: ==이미지와 동영상 같은 정적 파일, 로그, 백업, 데이터 레이크, ML 학습 데이터셋과 모델 체크포인트 저장에 주로 씀.==
-   **구조**: 버킷 안에 key와 객체가 평평하게 매핑될 뿐 진짜 디렉터리 계층이 없음. 파일 스토리지는 실제 폴더 트리가 있고, 블록 스토리지는 구조 자체가 없어서 OS가 파일시스템을 올려야 하며, DB는 스키마로 데이터 구조를 정의함.
-   **접근 방식**: ==HTTP 기반 REST API(PUT, GET, DELETE, LIST)로 접근함. 파일시스템처럼 마운트해서 쓰는 게 기본이 아니고, SDK나 CLI로 요청을 보내는 방식임. 블록 스토리지는 디스크처럼 서버에 붙이고, 파일 스토리지는 NFS 같은 프로토콜로 마운트하며, DB는 SQL이나 전용 쿼리 언어로 접근함.==
-   **데이터 찾기**: key나 prefix로만 찾을 수 있음. 파일 스토리지는 경로로 찾고, DB는 조건 검색, 정렬, 집계, 조인까지 가능하다는 게 가장 큰 차이임.
-   **메타데이터**: 객체마다 사용자 정의 메타데이터를 풍부하게 붙일 수 있음. 파일 스토리지는 이름, 크기, 권한 같은 고정 속성 위주이고, 블록 스토리지는 메타데이터 개념이 거의 없음.
-   **대표 서비스**: ==AWS S3, Google Cloud Storage, Azure Blob Storage==가 있고, 온프레미스에서는 MinIO, Ceph 같은 S3 호환 솔루션을 많이 씀.

## 용어

### Amazon S3

다른 이름: S3 · AWS S3

AWS의 객체 스토리지 서비스다. 버킷·객체·키로 데이터를 관리하고 스토리지 클래스·수명 주기·버전 관리 등을 제공한다.

### Cloudflare R2

다른 이름: R2

Cloudflare의 객체 스토리지 서비스다. S3 호환 API를 제공하며 Synapse의 이미지 파일 저장에 사용한다. 지원 API·권한·가격 조건은 S3와 별도로 확인한다.

### Google Cloud Storage

다른 이름: GCS

Google Cloud의 객체 스토리지 서비스다. 버킷과 객체를 중심으로 데이터를 보관하며 관리·보존·클래스 기능을 제공한다.

### Azure Blob Storage

Azure의 비정형 데이터 저장 서비스다. Blob 컨테이너는 저장 구획을 뜻하며 Docker 실행 컨테이너와 다른 개념이다.

### 버킷 · 객체 · 키

버킷은 객체를 담는 논리적 구획, 객체는 데이터와 메타데이터, 키는 해당 구획에서 객체를 식별하는 이름이다.

### Presigned URL

다른 이름: 서명된 URL

허용된 작업·대상·유효 기간 등을 서명에 담아 특정 요청을 실행하게 하는 URL이다. URL을 가진 사람이 권한을 사용할 수 있으므로 공개 범위와 만료를 관리한다.

### 스토리지 클래스 · 수명 주기

접근 빈도·보존 요구에 따라 저장 클래스를 고르고, 시간이 지나면 이동·삭제하도록 정책을 설정한다. 조회 비용·최소 보관 기간·복구 시간을 함께 확인한다.

## 핵심 구조
객체 스토리지는 데이터 바이트와 메타데이터를 객체로 보관하고 버킷 안의 키로 식별한다. S3는 이 종류의 대표적인 제품이지 스토리지 전체를 뜻하는 이름은 아니다.

`images/photo.png`처럼 슬래시가 들어간 키도 사용할 수 있다. 일반적인 객체 API에서 이 표현은 파일 시스템의 디렉터리 계층과 같지 않다. 일부 서비스의 계층형 네임스페이스 기능은 별도로 확인한다.

## 접근과 변경
앱이 HTTP API나 SDK로 업로드·다운로드·목록 조회 등을 수행한다. 특정 바이트 영역을 다운로드하는 기능은 지원될 수 있지만, 일반적인 객체 API는 임의 위치를 디스크처럼 계속 덮어쓰는 인터페이스가 아니다. 수정한 파일은 보통 새 객체 버전·교체 업로드로 반영한다. 대용량 파일은 멀티파트 업로드를 검토한다.

## 적합한 용도와 제약
이미지·동영상·PDF·백업·분석 데이터 등 큰 비정형 원본을 보관하기 좋다. SQL JOIN이나 레코드 단위 트랜잭션이 필요한 업무 데이터를 객체 API만으로 처리하려고 하면 별도 인덱스·처리 시스템이 필요하다. 일반적인 DB의 로컬 데이터 디스크를 객체 저장소 마운트로 단순 대체하지 않는다. 객체 저장소를 저장 계층으로 설계한 DB·분석 시스템은 별개의 경우다.

## 업로드 서비스 설계
1. DB에서 사용자·파일 권한과 업로드 상태를 관리한다.
2. 앱 서버가 파일을 중계하거나, 제한된 서명 URL을 발급해 클라이언트가 직접 업로드하도록 한다.
3. 완료 확인·형식·크기 검증 후 메타데이터 상태를 갱신한다.
4. 미완료 업로드·고아 객체·삭제 실패를 정리한다.

S3·R2·GCS·Azure Blob은 같은 역할을 맡을 수 있지만 API·권한·정합성·기능·가격이 모두 같지는 않다. S3 호환이라는 표현도 모든 S3 기능과 운영 특성의 동일성을 뜻하지 않는다.
