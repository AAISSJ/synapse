# 커넥션 풀

다른 이름: Connection Pool · 연결 풀

주제: DB

DB 연결을 재사용하고 동시 연결 수와 대기 시간을 통제하는 자원 관리 방식.

## 용어

### max pool size

다른 이름: 최대 풀 크기

풀의 최대 연결 수. 전체 앱 인스턴스·워커·서비스·운영 접속을 합한 DB 연결 예산을 고려한다.

### min idle

다른 이름: 최소 유휴 연결

트래픽이 없을 때도 유지하는 유휴 연결 수. 필요 이상의 연결을 붙잡지 않도록 설정한다.

### acquisition timeout

다른 이름: 대기 타임아웃

사용 가능한 연결을 빌릴 때 기다리는 최대 시간. 쿼리 실행 제한 시간과 구분한다.

### max lifetime

다른 이름: 최대 연결 수명

연결 교체 기준 수명. DB·방화벽·프록시의 연결 제한과 함께 설정한다.

### 연결 누수

반환되지 않는 연결 때문에 풀이 고갈되는 문제. finally/컨텍스트 관리자 등으로 반환을 보장한다.

## 동작 원리
커넥션 풀은 DB 연결을 재사용 가능한 자원으로 관리한다. 요청은 연결을 빌려 쿼리·트랜잭션을 실행하고, 완료 후 풀에 반환한다. TCP/TLS 연결·인증·세션 초기화 비용을 줄이면서 동시 연결 수를 제한한다.

| 설정 | 의미 |
| --- | --- |
| max pool size | 동시에 사용할 수 있는 연결 수의 상한 |
| min idle | 유지할 최소 유휴 연결 수 |
| acquisition timeout | 연결 획득을 기다리는 최대 시간 |
| max lifetime | 연결을 교체하는 기준 수명 |

## 운영 기준
==전체 앱 인스턴스·워커·관리 작업의 연결 수와 여유분을 합해 DB 연결 예산을 정한다.== 풀을 키우는 것만으로 처리량이 늘지는 않는다. DB CPU·락 경합과 풀 대기 시간을 함께 관찰해야 한다.

트랜잭션은 필요한 구간만 연결을 점유하고, 예외가 나도 연결 반환을 보장한다. 대표 구현은 HikariCP, SQLAlchemy 풀, Go database/sql이며 PostgreSQL 외부 풀러로 PgBouncer를 사용할 수 있다.

Redis 비동기 클라이언트의 멀티플렉싱은 일반적인 RDB 연결 풀과 동작 방식이 다르므로 클라이언트별 연결 모델을 확인한다.
