# 배포 전략

다른 이름: Deployment Strategies · 배포 방식

주제: 설계

새 버전의 배치·트래픽 노출·운영 검증·복구 방식을 설계한다. 인프라 교체와 기능 릴리스를 구분하고 가용성·호환성·비용에 맞춰 전략을 조합한다.

## 내 정리

- **인스턴스 교체·트래픽 전환**: Recreate, Rolling, Blue-Green, Canary.
- **검증과 실험**: Shadow는 응답 경로 밖에서 동작을 비교하고, A/B는 사용자 행동·비즈니스 효과를 실험한다.
- **기능 릴리스 제어**: Feature Flag로 배포와 노출을 분리한다. Dark Launch는 사용자에게 드러내지 않은 운영 실행·검증이다.

## 인스턴스 교체·트래픽 전환

| 방식 | 동작 | 가용성·추가 자원 조건 | 복귀 방식 | 선택 기준 |
| --- | --- | --- | --- | --- |
| Recreate | 기존 인스턴스를 종료한 뒤 새 버전을 시작 | 전환 공백을 허용. 구·신 앱의 동시 실행 용량은 불필요할 수 있음 | 이전 버전을 다시 시작 | 단순함과 동시 버전 회피가 중요하고 중단을 허용할 때 |
| Rolling | 인스턴스를 순차 교체 | 정상 인스턴스·readiness·종료 처리가 필요. 자원은 surge·비가용량 설정에 따름 | 구 버전으로 순차 재교체 | 호환성을 유지하면서 점진적으로 교체할 때 |
| Blue-Green | 별도 환경을 검증한 뒤 라우팅 전환 | 전환 중 앱 환경 두 세트 가까이 필요할 수 있음. 연결·데이터 호환성도 확인 | 기존 환경으로 라우팅 복귀. 데이터 복구는 별도 | 빠른 트래픽 전환·복귀가 중요할 때 |
| Canary | 제한된 요청·사용자에 노출한 뒤 확대 | 라우팅·충분한 표본·관측 필요. 최소 인스턴스·모델 용량은 별도 확보 | 새 버전 비율 축소·중단 | 실제 운영에서 영향 범위를 제한하며 안전성을 검증할 때 |


### 1. 재생성 · Recreate
기존 버전을 전부 종료하고 새 버전을 시작한다. 구조가 단순하고 구·신 버전의 동시 실행을 피할 수 있지만 서비스 공백이 발생한다. 개발·검증 환경이나 중단을 허용하는 서비스에 적합하다. 배치 작업은 진행 중인 작업의 중단·중복·재시작 조건까지 확인해야 한다.

### 2. 롤링 업데이트 · Rolling Update
인스턴스를 조금씩 교체한다. Kubernetes Deployment의 기본 전략이며 maxSurge와 maxUnavailable로 추가 Pod와 비가용 Pod의 허용량을 조절한다.

무중단은 자동 보장이 아니다. 충분한 정상 인스턴스·여유 용량, readiness, 연결 드레이닝, graceful shutdown과 클라이언트 재시도가 맞아야 한다. 교체 중 구·신 버전이 동시에 요청·메시지를 처리하므로 API·이벤트·스키마 호환성이 필요하다. 롤백도 재교체 과정이어서 트래픽 스위치 방식보다 시간이 걸릴 수 있다.

### 3. 블루-그린 · Blue-Green
==운영 중인 Blue와 별도로 Green을 준비해 새 버전을 검증하고 라우팅 대상을 전환==한다. 기존 환경을 유지하면 트래픽을 빠르게 되돌릴 수 있다.

앱 계층 용량은 전환 기간에 두 세트 가까이 필요할 수 있지만 DB 등 모든 자원이 반드시 두 배가 되는 것은 아니다. 로드밸런서·DNS·장기 연결의 특성에 따라 전환과 복귀가 즉시 완료되지 않을 수 있다.

양쪽 앱이 같은 DB를 사용할 수도, 별도 데이터 계층을 둘 수도 있다. 전자는 구·신 코드의 스키마 호환성, 후자는 데이터 동기화·쓰기 전환·분기 방지가 핵심이다. 새 버전이 만든 데이터나 외부 부작용은 라우팅을 되돌린다고 없어지지 않는다.

### 4. 카나리 · Canary
==일부 운영 트래픽을 새 버전에 보내고 점차 확대한다==. 1% → 5% → 25% → 100%는 예시이며 서비스의 트래픽 규모와 위험도에 맞춰 단계·관측 시간을 정한다.

- 버전별 오류율, p95·p99 지연, 자원 사용량과 핵심 품질 지표를 비교한다.
- 낮은 비율의 표본이 충분한지, 피크·배치·특정 고객 경로를 포함했는지 확인한다.
- 중단 기준, 관측 기간, 승인·자동 승격 조건을 배포 전에 정한다.
- 가중치 라우팅과 사용자·세션 단위의 일관된 배정이 필요한지 결정한다.

Istio 같은 트래픽 계층이나 Argo Rollouts·Flagger 같은 롤아웃 도구를 사용할 수 있다. 도구마다 필요한 라우터·분석 시스템과 지원 기능은 다르다. 단순히 새 인스턴스를 하나 더 띄운 것만으로 정밀한 트래픽 비율이 보장되지는 않는다.

### 점진적 전달 · Progressive Delivery
카나리·피처 플래그·분석 등을 조합해 노출 범위를 제한하고 관측 결과와 정책에 따라 확대하는 접근이다. 트래픽 분배 자체와 승격·중단 판단을 함께 설계한다.

## 검증과 실험

### 5. A/B 테스트
배포 안전성보다 기능이 사용자 행동과 비즈니스 결과에 미치는 효과를 비교하는 실험이다. 보통 사용자 ID 등을 이용해 무작위로 그룹을 배정하고 동일 사용자의 배정을 유지한다.

지역·헤더 조건으로만 그룹을 나누면 사용자의 특성이나 트래픽이 달라 결과가 편향될 수 있다. 표본 크기·실험 기간·통계적 판단과 함께 오류율·이탈률 같은 가드레일을 둔다. 안전한 카나리 이후 A/B를 수행하거나 피처 플래그로 실험군을 노출하는 등 조합할 수 있다.

| 방식 | 검증하려는 것 | 사용자에게 전달하는 응답 | 지표·판단 기준 | 비용·주의사항 |
| --- | --- | --- | --- | --- |
| A/B 테스트 | 기능·경험이 사용자 행동과 비즈니스 결과에 미치는 효과 | 실험군별로 실제 다른 기능·응답을 노출 | 전환율·클릭률·유지율 등. 무작위 배정, 일관된 그룹, 표본 크기와 실험 기간을 설계 | 실험군은 새 기능의 영향을 받음. 편향과 오류율 등 안전 가드레일을 관리 |
| Shadow / Mirroring | 새 구현의 결과·성능·품질과 운영 적합성 | 사용자에게는 기존 구현의 응답만 전달 | 결과 차이·지연·자원 사용. 비결정적 모델은 문자열 일치 외 평가 필요 | 복제율에 따라 추가 자원 필요. 쓰기·결제·알림 부작용과 민감 정보, 공유 자원 부하를 통제 |

### 6. 섀도우 · Shadow / Mirroring
운영 요청을 새 버전에도 복제하지만 새 응답은 사용자에게 전달하지 않는다. 기존 버전이 사용자 응답을 담당하는 동안 새 구현의 결과·지연·자원 사용을 비교한다.

사용자 응답 경로 밖이라고 무위험한 것은 아니다. 복제 부하가 공유 자원을 압박할 수 있고, 요청에 개인정보나 비밀이 들어갈 수 있다. 결제·메일·쓰기 요청 등은 외부 부작용을 차단하거나 격리된 대상에 보내야 한다. 단순한 요청 복제에 멱등성 키만 붙인다고 모든 부작용이 방지되는 것은 아니다.

### LLM 서빙 적용 예시
**호환성·기준 평가 → 제한된 Shadow → Canary → 전체 전환** 순서를 검토할 수 있다. 모든 단계가 필수인 것은 아니다.

- 오프라인 평가로 품질·안전성·도구 호출 형식과 API 호환성을 확인한다.
- 민감 정보와 부작용을 통제한 표본을 Shadow로 보내 결과 품질·지연·GPU 메모리를 비교한다. 비결정적 출력은 문자열 일치만으로 평가하지 않는다.
- Canary에서 오류율·첫 토큰 지연(TTFT)·토큰 처리량·비용·품질을 버전별로 관측한다. 세션의 모델 배정도 필요에 따라 유지한다.
- 승격·중단 기준을 충족하면 확대한다. 기존 모델을 유지할 용량과 복귀 시간을 미리 정한다.

트래픽이 1%여도 새 모델 전체 가중치와 최소 GPU 용량은 필요할 수 있다. Shadow와 Blue-Green 모두 상당한 추가 비용이 들 수 있으므로 ‘Canary면 항상 저렴하다’고 단정하지 않는다.

## 기능 릴리스 제어

| 구분 | 의미 | 사용자 노출 | 구현·조합 | 종료·복구 시 주의 |
| --- | --- | --- | --- | --- |
| Feature Flag | 배포된 기능의 실행·노출을 조건별로 제어하는 수단 | 사용자·조직·비율 등에 따라 켜고 끌 수 있음 | 설정 서비스·앱 분기. Canary·A/B·Dark Launch와 조합 가능 | off 전파 지연과 기본값을 설계. 이미 발생한 데이터 변경·외부 부작용은 취소되지 않음 |
| Dark Launch | 기능을 드러내지 않은 채 운영 환경에서 실행·검증하는 방식 | 새 기능의 결과를 사용자에게 보여주지 않음 | 플래그로 숨긴 백엔드 실행이나 Shadow 활용. 코드를 배포해 두고 전혀 실행하지 않는 상태와 구분 | 실행을 중단해도 이미 생긴 부작용은 별도 처리. 검증용 부하·데이터 접근 통제 필요 |

### 7. 피처 플래그와 다크 론치
Feature Flag는 코드가 배포된 상태에서 기능의 실행·노출 범위를 제어한다. 사용자·조직·비율별로 켜거나 문제가 생기면 끌 수 있다. 플래그 배포 지연과 캐시, 안전한 기본값도 고려한다.

Dark Launch는 기능을 사용자에게 보여주지 않은 채 운영에서 실행·검증하는 방식이다. 플래그로 숨긴 백엔드 실행이나 Shadow를 활용할 수 있다. 코드를 배포해 두고 전혀 실행하지 않는 상태와는 다르다.

플래그에는 담당자·목적·제거 시점을 정한다. 오래 남은 플래그는 분기 조합과 테스트 비용을 늘린다. 플래그 off는 해당 경로를 멈추는 것이며 이미 반영된 데이터 변경을 취소하는 작업은 아니다.

## 용어

### 재생성 배포

다른 이름: Recreate

기존 버전을 종료한 뒤 새 버전을 시작한다. 구·신 버전의 동시 실행을 피할 수 있지만 서비스 공백과 복구 시간이 발생할 수 있다.

### 롤링 업데이트

다른 이름: Rolling Update · Rolling

인스턴스를 순차 교체한다. 교체 중 구·신 버전이 공존하므로 API·이벤트·DB 스키마 호환성이 필요하다. readiness·종료 처리·용량 설정이 무중단 여부를 좌우한다.

### 블루-그린 배포

다른 이름: Blue-Green · 블루그린

기존 환경과 별도의 새 환경을 준비·검증한 뒤 트래픽 대상을 전환한다. 기존 환경을 유지하면 빠르게 복귀할 수 있지만 데이터 변경과 진행 중 요청까지 자동 복구되지는 않는다.

### 카나리 배포

다른 이름: Canary · 카나리

일부 사용자·요청에 새 버전을 노출하고 버전별 오류율·지연·품질을 비교하며 범위를 늘린다. 비율뿐 아니라 표본 수·관측 시간·중단 기준이 중요하다.

### A/B 테스트

다른 이름: A/B Test

사용자를 실험군·대조군에 보통 무작위로 배정하고 전환율 등 결과를 비교한다. 배정은 일관되게 유지하며 편향·표본 크기·유의성·안전 지표를 함께 관리한다.

### 섀도우 트래픽

다른 이름: Shadow · Mirroring · Traffic Mirroring

실제 요청을 복제해 새 구현에도 보내되 사용자 응답은 기존 구현에서 제공한다. 복제된 요청의 쓰기·결제·알림을 차단하거나 격리하고 추가 부하와 정보 노출을 통제해야 한다.

### 피처 플래그

다른 이름: Feature Flag

실행 중 조건·사용자·비율에 따라 기능을 켜고 끄는 제어 수단이다. 배포와 릴리스를 분리한다. 플래그를 꺼도 이미 저장한 데이터나 외부 부작용이 취소되지는 않는다.

### 다크 론치

다른 이름: Dark Launch

기능을 사용자에게 드러내지 않은 채 운영 환경에서 실행·검증하는 방식이다. 피처 플래그나 섀도우 트래픽으로 구현할 수 있으며 단순히 코드를 꺼둔 상태와는 구분한다.

### 점진적 전달

다른 이름: Progressive Delivery

기능·버전을 제한된 범위에 노출하고 관측 결과와 정책에 따라 범위를 확대하는 운영 접근이다. 카나리·플래그·자동 분석 등을 조합할 수 있다.

### readiness 검사

다른 이름: Readiness Probe

인스턴스가 실제 요청을 받을 준비가 되었는지 판단한다. 프로세스가 살아 있다는 liveness와 목적이 다르다.

### maxSurge · maxUnavailable

다른 이름: maxSurge · maxUnavailable

Kubernetes 롤링 업데이트에서 각각 목표 수를 초과해 띄울 Pod 수와 사용할 수 없어도 되는 Pod 수를 정한다. 새 Pod가 준비되지 않으면 교체 진행이 제한된다.

### graceful shutdown

다른 이름: 정상 종료 · Connection Draining

새 요청 유입을 멈추고 진행 중 작업을 마무리한 뒤 종료하는 과정이다. 연결 드레이닝·종료 유예 시간·재시도·멱등성을 함께 고려한다.

### expand-contract

다른 이름: 확장-축소 마이그레이션

새·구 버전이 공존할 수 있게 스키마나 API를 먼저 확장하고, 전환·데이터 이동이 완료된 뒤 기존 구조를 제거하는 변경 절차다.

### 롤백 · 롤포워드

다른 이름: Rollback · Roll Forward

롤백은 이전 코드·설정으로 복귀하고, 롤포워드는 수정 버전을 추가 배포해 문제를 해결한다. 비가역적인 데이터 변경이 있으면 코드 롤백만으로 복구할 수 없다.

## 배포 전략 · 동작 원리와 선택 기준

- **인스턴스 교체·트래픽 전환**: Recreate, Rolling, Blue-Green, Canary.
- **검증과 실험**: Shadow는 응답 경로 밖에서 동작을 비교하고, A/B는 사용자 행동·비즈니스 효과를 실험한다.
- **기능 릴리스 제어**: Feature Flag로 배포와 노출을 분리한다. Dark Launch는 사용자에게 드러내지 않은 운영 실행·검증이다.

## 인스턴스 교체·트래픽 전환

### 1. 재생성 · Recreate
기존 버전을 전부 종료하고 새 버전을 시작한다. 구조가 단순하고 구·신 버전의 동시 실행을 피할 수 있지만 서비스 공백이 발생한다. 개발·검증 환경이나 중단을 허용하는 서비스에 적합하다. 배치 작업은 진행 중인 작업의 중단·중복·재시작 조건까지 확인해야 한다.

### 2. 롤링 업데이트 · Rolling Update
인스턴스를 조금씩 교체한다. Kubernetes Deployment의 기본 전략이며 maxSurge와 maxUnavailable로 추가 Pod와 비가용 Pod의 허용량을 조절한다.

무중단은 자동 보장이 아니다. 충분한 정상 인스턴스·여유 용량, readiness, 연결 드레이닝, graceful shutdown과 클라이언트 재시도가 맞아야 한다. 교체 중 구·신 버전이 동시에 요청·메시지를 처리하므로 API·이벤트·스키마 호환성이 필요하다. 롤백도 재교체 과정이어서 트래픽 스위치 방식보다 시간이 걸릴 수 있다.

### 3. 블루-그린 · Blue-Green
운영 중인 Blue와 별도로 Green을 준비해 새 버전을 검증하고 라우팅 대상을 전환한다. 기존 환경을 유지하면 트래픽을 빠르게 되돌릴 수 있다.

앱 계층 용량은 전환 기간에 두 세트 가까이 필요할 수 있지만 DB 등 모든 자원이 반드시 두 배가 되는 것은 아니다. 로드밸런서·DNS·장기 연결의 특성에 따라 전환과 복귀가 즉시 완료되지 않을 수 있다.

양쪽 앱이 같은 DB를 사용할 수도, 별도 데이터 계층을 둘 수도 있다. 전자는 구·신 코드의 스키마 호환성, 후자는 데이터 동기화·쓰기 전환·분기 방지가 핵심이다. 새 버전이 만든 데이터나 외부 부작용은 라우팅을 되돌린다고 없어지지 않는다.

### 4. 카나리 · Canary
일부 운영 트래픽을 새 버전에 보내고 점차 확대한다. 1% → 5% → 25% → 100%는 예시이며 서비스의 트래픽 규모와 위험도에 맞춰 단계·관측 시간을 정한다.

- 버전별 오류율, p95·p99 지연, 자원 사용량과 핵심 품질 지표를 비교한다.
- 낮은 비율의 표본이 충분한지, 피크·배치·특정 고객 경로를 포함했는지 확인한다.
- 중단 기준, 관측 기간, 승인·자동 승격 조건을 배포 전에 정한다.
- 가중치 라우팅과 사용자·세션 단위의 일관된 배정이 필요한지 결정한다.

Istio 같은 트래픽 계층이나 Argo Rollouts·Flagger 같은 롤아웃 도구를 사용할 수 있다. 도구마다 필요한 라우터·분석 시스템과 지원 기능은 다르다. 단순히 새 인스턴스를 하나 더 띄운 것만으로 정밀한 트래픽 비율이 보장되지는 않는다.

### 점진적 전달 · Progressive Delivery
카나리·피처 플래그·분석 등을 조합해 노출 범위를 제한하고 관측 결과와 정책에 따라 확대하는 접근이다. 트래픽 분배 자체와 승격·중단 판단을 함께 설계한다.

### DB 변경과 롤백의 공통 원칙
1. 롤백 대상이 코드·설정·트래픽·데이터 중 무엇인지 분리한다.
2. 구·신 앱이 공존한다면 expand-contract를 사용한다. 새 컬럼·형식을 먼저 추가하고 호환 코드를 배포한 뒤 데이터를 이동·검증하며, 마지막에 기존 구조를 제거한다.
3. 삭제·의미 변경 같은 비가역 작업 전에 복구 방법을 검증한다. 코드 롤백이 불가능하면 롤포워드로 수정할 수 있어야 한다.
4. 재시도·중복 작업·진행 중 요청에 대비해 멱등성, 연결 드레이닝과 관측을 마련한다.

## 검증과 실험

### 5. A/B 테스트
배포 안전성보다 기능이 사용자 행동과 비즈니스 결과에 미치는 효과를 비교하는 실험이다. 보통 사용자 ID 등을 이용해 무작위로 그룹을 배정하고 동일 사용자의 배정을 유지한다.

지역·헤더 조건으로만 그룹을 나누면 사용자의 특성이나 트래픽이 달라 결과가 편향될 수 있다. 표본 크기·실험 기간·통계적 판단과 함께 오류율·이탈률 같은 가드레일을 둔다. 안전한 카나리 이후 A/B를 수행하거나 피처 플래그로 실험군을 노출하는 등 조합할 수 있다.

### 6. 섀도우 · Shadow / Mirroring
운영 요청을 새 버전에도 복제하지만 새 응답은 사용자에게 전달하지 않는다. 기존 버전이 사용자 응답을 담당하는 동안 새 구현의 결과·지연·자원 사용을 비교한다.

사용자 응답 경로 밖이라고 무위험한 것은 아니다. 복제 부하가 공유 자원을 압박할 수 있고, 요청에 개인정보나 비밀이 들어갈 수 있다. 결제·메일·쓰기 요청 등은 외부 부작용을 차단하거나 격리된 대상에 보내야 한다. 단순한 요청 복제에 멱등성 키만 붙인다고 모든 부작용이 방지되는 것은 아니다.

| --- | --- | --- | --- | --- |
| A/B 테스트 | 기능·경험이 사용자 행동과 비즈니스 결과에 미치는 효과 | 실험군별로 실제 다른 기능·응답을 노출 | 전환율·클릭률·유지율 등. 무작위 배정, 일관된 그룹, 표본 크기와 실험 기간을 설계 | 실험군은 새 기능의 영향을 받음. 편향과 오류율 등 안전 가드레일을 관리 |

### LLM 서빙 적용 예시
**호환성·기준 평가 → 제한된 Shadow → Canary → 전체 전환** 순서를 검토할 수 있다. 모든 단계가 필수인 것은 아니다.

- 오프라인 평가로 품질·안전성·도구 호출 형식과 API 호환성을 확인한다.
- 민감 정보와 부작용을 통제한 표본을 Shadow로 보내 결과 품질·지연·GPU 메모리를 비교한다. 비결정적 출력은 문자열 일치만으로 평가하지 않는다.
- Canary에서 오류율·첫 토큰 지연(TTFT)·토큰 처리량·비용·품질을 버전별로 관측한다. 세션의 모델 배정도 필요에 따라 유지한다.
- 승격·중단 기준을 충족하면 확대한다. 기존 모델을 유지할 용량과 복귀 시간을 미리 정한다.

트래픽이 1%여도 새 모델 전체 가중치와 최소 GPU 용량은 필요할 수 있다. Shadow와 Blue-Green 모두 상당한 추가 비용이 들 수 있으므로 ‘Canary면 항상 저렴하다’고 단정하지 않는다.

## 기능 릴리스 제어

### 7. 피처 플래그와 다크 론치
Feature Flag는 코드가 배포된 상태에서 기능의 실행·노출 범위를 제어한다. 사용자·조직·비율별로 켜거나 문제가 생기면 끌 수 있다. 플래그 배포 지연과 캐시, 안전한 기본값도 고려한다.

Dark Launch는 기능을 사용자에게 보여주지 않은 채 운영에서 실행·검증하는 방식이다. 플래그로 숨긴 백엔드 실행이나 Shadow를 활용할 수 있다. 코드를 배포해 두고 전혀 실행하지 않는 상태와는 다르다.

플래그에는 담당자·목적·제거 시점을 정한다. 오래 남은 플래그는 분기 조합과 테스트 비용을 늘린다. 플래그 off는 해당 경로를 멈추는 것이며 이미 반영된 데이터 변경을 취소하는 작업은 아니다.
